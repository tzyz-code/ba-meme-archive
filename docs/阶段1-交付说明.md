# 表情档案馆 · 阶段 1 交付说明

## 一、本阶段做了什么

产出**可交互的高保真前端原型**，5 个页面 + 设计系统 + 模拟数据层。
纯静态、零依赖、零构建，`node server.js` 起一个静态服务器即可打开。

## 二、核心设计决策：把游戏设定做成界面语言

游戏名里的「档案」两个字是现成的视觉资产。整站被设计成一座**表情档案馆**：

| 视觉元素 | 对应含义 |
|---|---|
| 档案编号章 `No.0231` | 每张图有唯一编号，赋予收藏感与可引用性 |
| 蓝色「BA」专属角标 | 蔚蓝档案的视觉特权，搜索与列表中永远置顶 |
| 蓝色 2px 内描边（`.card--ba`） | 蔚蓝档案卡片在密集网格中一眼可辨 |
| 档案馆网格底纹 | hero 区背景，强化"检索大厅"的空间感 |
| 其它 IP 用灰色虚线/描边徽章 | 视觉降权，不与主 IP 争夺注意力 |

## 三、排序权重设计（核心需求落地处）

```
最终分 = 文本相关性
       + 0.35 × IP权重
       + 0.20 × 热度归一(log10)
       + 0.15 × 时效归一(指数衰减)
       + 0.03 × 识别置信度
```

IP 权重表：

| IP | 权重 | 得分贡献 | 视觉 |
|---|---|---|---|
| 蔚蓝档案 | **1.00** | **0.35** | 实心蓝徽章 + 蓝色描边 |
| 其它游戏 IP | 0.30 | 0.105 | 灰色描边徽章 |
| 通用表情（无IP） | 0.10 | 0.035 | 虚线徽章 |

即：同等相关度下，蔚蓝档案条目得分约为其它游戏 IP 的 **3.3 倍**，这是"权重更高、优先级更高"的量化实现。

文本相关性采用多字段加权匹配（标题 ×3.0 / 角色中文名 ×2.5 / 角色英文名 ×1.5 / 梗文关键词 ×1.2 / 编号 ×1.0），支持完全匹配、包含匹配、逐字模糊匹配三级降级。

## 四、文件结构

```
meme-archive/
└─ public/
   ├─ index.html          档案大厅（hero 检索 + 角色馆 + 瀑布流）
   ├─ search.html         搜索结果（含完整筛选与排序切换）
   ├─ upload.html         上传入库（含模拟识图流程）
   ├─ detail.html         档案详情（含 SEO 结构化数据预埋）
   ├─ about.html          关于 + 版权声明 + 排序规则说明
   └─ assets/
      ├─ css/tokens.css      设计令牌（色彩/排版/间距/阴影/动效）
      ├─ css/components.css  组件层（档案卡/徽章/筛选器/上传区…）
      └─ js/data.js          模拟数据 + 排序算法 + 渲染函数
```

## 五、已验证项

- 5 个页面 + 全部静态资源均返回 HTTP 200
- 排序算法已用真实角色数据验证：搜索「白子」→ 白子条目排前；搜索「猫猫」→ 通用表情命中
- 筛选器（IP/角色/情绪）、排序切换（推荐/最热/最新/识别最准）、收藏（localStorage）均已实现
- 上传页识图流程为 5 步动画模拟，阶段 3 替换为真实模型调用
- 详情页已预埋 `ImageObject` 结构化数据，阶段 4 改为服务端渲染

## 六、阶段 2 的接入点

原型与后端之间只有**一个数据文件**的依赖：

- `data.js` 中的 `MEMES` 数组 → 替换为 `fetch('/api/search?...')`
- `search()` 函数 → 移到服务端执行（因为 FTS5 全文检索必须在服务端）
- `upload.html` 中的 `runRecognize()` → 替换为 `POST /api/recognize`
- `cardHTML()` / `getMeme()` 保留，前端渲染逻辑基本不用动

这意味着阶段 2 是**追加**而不是重写，前端工作不会浪费。
